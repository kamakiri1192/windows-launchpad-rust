# AIによるフォルダ整理補助仕様（任意機能）

- 作成日: 2026-09-25
- 状態: 実装前の提案仕様。API接続・精度評価・審査通過を確認した文書ではない。
- 対象: Liquid StartのWindows版およびmacOS版。Windows版はMicrosoft Storeへの提出を想定する。
- 基本機能: [初期フォルダ配置仕様（非AI）](INITIAL_FOLDER_LAYOUT_SPEC.md)。本機能とは独立して実装・出荷できる。

## 1. 決定事項

**固定ルールで初期配置を完成させ、AIは未対応アプリの所属候補を補う任意機能にする。**

| 項目 | 採用する仕様 |
| --- | --- |
| 初期状態 | 外部送信は無効。端末内だけでランチャーを利用できる |
| AIの役割 | 未確定アプリを、提示した製品群候補のどれに入れるか判断する |
| 検討する方式 | Jevのような選択式の判定サービス。特定モデルへdomainを依存させない |
| 入れない判断 | 必ず`none`を用意する。低品質・不明・矛盾した結果は不採用 |
| 送信の許可 | 初めて利用するときに説明と一つの有効化操作を設け、同じ範囲の許可を保存する |
| 再確認 | API呼び出しごと・アプリごと・起動ごとの同意ダイアログは出さない |
| 配置への反映 | 結果のプレビュー後に一括適用する。返答が来ただけでは配置を変更しない |
| 失敗時 | 端末内で完成した配置をそのまま維持する |
| 継続整理 | 行わない。起動・追加インストール・定期スキャンをAI呼び出しの契機にしない |

AIによる外部送信の許可と、配置変更の適用は別の操作である。プレビュー後の「適用」は同意の取り直しではなく、変更結果を確定する通常操作とする。

## 2. 基本機能との境界

非AIのルール結果を次のように扱う。

| 基本機能の結果 | AIの扱い |
| --- | --- |
| `Grouped(preset_id)` | 変更しない。既知の所属先として利用する |
| `KeepTopLevel` | 変更しない。AIへの判定対象から除外する |
| `Unresolved` | 判定候補にできる。ただし送信対象の条件も満たすこと |

用途別カテゴリ、自由なフォルダ名の生成、同じアプリの多重掲載、アプリのインストール・削除・起動、使用頻度の推定は対象外とする。既存の[Issue #38](https://github.com/kamakiri1192/windows-launchpad-rust/issues/38)の代替実装にはしない。

初版は**初期配置が未編集の間の補完**に限定する。基本機能の初期化記録と改訂番号で確認する。既存ユーザーや手動編集後の配置を一括で整理し直す機能は含めない。この制約はUIにも表示し、既存の並び替えを黙って上書きしない。

## 3. ユーザー体験

### 3.1 初回の導線

最初から端末内の整理結果を表示する。AIを使うかどうかを、最初のアプリ起動の前に必須で選ばせない。

初期配置が未編集で対象候補がある場合に限り、任意の導線「AIで整理を補う」を表示する。閉じた案内を毎回表示しない。条件を満たす間は設定からも開ける。

初めて選択したときの説明例は次のとおり。実装時には実際の運営者・送信先・項目に一致する文面へ確定する。

> AIで初期整理を補います。対象アプリの製品情報をLiquid Startの運営サーバーと外部AIサービスへ送信します。端末内だけでも利用できます。結果を確認してから配置へ適用します。
>
> 送信先: ［運営者名］ / ［AIサービス名］
>
> ［送信内容を確認］ ［プライバシーポリシー］
>
> ［AIを有効にして提案を作る］ ［端末内だけで続ける］

ボタンを押す前に共有範囲を読めること。初期状態で有効なチェックボックス、閉じる操作による有効化、規約リンクだけに隠した外部送信の説明は禁止する。説明済みの有効化ボタンの後に同じ確認ダイアログを重ねない。

### 3.2 提案と適用

1. 現在の配置と検出情報の改訂番号を取得し、処理対象を固定する。
2. 送信対象と候補を端末内で準備し、外部通信を開始する。元のグリッドは利用可能に保つ。
3. 受け取った結果を検証し、採用できる変更だけをプレビューに表示する。
4. プレビューは「新しいフォルダ」「追加されるアプリ」「変更しないアプリ」を区別し、通常のフォルダ名と小アイコンで示す。個々の変更候補を外せるようにする。
5. ユーザーの「適用」で改訂番号を再確認し、一括保存する。「変更しない」では元の配置を維持する。

AI処理中に手動編集や検出対象の変更があれば結果を古いものとして破棄する。自動的に新しい配置へ結果を当て直さない。利用者へ再実行を案内できるのは、初期配置の未編集条件をなお満たす場合だけとする。

適用結果は通常のフォルダである。以降は基本機能と同じく自動更新しない。AIを無効にしても既に適用した配置を勝手に解体しない。

### 3.3 取り消し

AI適用直前の配置を一世代だけ保存し、変更が入るまで「AIの変更を戻す」を提供する。基本機能の初期整理の取り消しとは別の記録にする。

後の手動編集や検出差分で改訂番号が変わった場合は取り消しを無効にする。取り消し操作で古い非表示状態や消えたアプリを復元しない。AIを戻した場合も、基本機能の古い取り消し権限を自動復活させない。

## 4. AIへ渡す候補と判定契約

### 4.1 候補の作り方

同梱プリセットを基本候補とする。必要に応じて、端末内で取得した製品名や元の製品固有フォルダから追加候補を組み立てる。この追加候補はAI拡張側の提案であり、基本機能のプリセットを自動更新しない。

- 「製品群として一緒に置く意味があるか」を問う。仕事・娯楽などの用途カテゴリを新設しない。
- メーカー名だけ、一般的なディレクトリ名、文字列の単なる共通接頭辞だけで候補を確定しない。
- 追加候補は2個以上の異なる候補アプリがある場合に限る。フォルダ名は確認可能な製品群名から端末内で作り、AIの自由生成は使わない。
- 候補IDは端末内のプリセットまたは今回の提案に対応付ける。表示名だけで既存のユーザーフォルダへ結び付けない。
- 必ず`none`（該当なし・判断不能）を含める。`none`というフォルダは作らない。

Jevを採用する場合も、このアプリ側の判定契約をアダプタで実現する。モデル/APIの名称・パラメータ・候補上限・対応言語は提供元の仕様を再確認して固定する。過去の会話で挙げたモデル名や速度を本番保証として採用しない。

### 4.2 判定結果

内部結果は少なくとも、要求内のアプリ参照、候補IDまたは`none`、任意の確信度、モデル版を含む。アダプタは提供元のレスポンスをこの形へ変換する。これはLiquid Start内部の契約であり、JevのHTTPレスポンス例ではない。

AIの確信度を「実際に正解である確率」としてUIに表示しない。確信度や候補分布を利用する場合の採用閾値は評価データから決める。固定ルールへの一致、2個以上の条件、アプリ集合の保存、配置の一意性はAIではなく通常コードで検証する。

## 5. 外部送信データ

### 5.1 ローカル情報を直接シリアライズしない

`SnapshotEntry`、`AppRecord`、`LauncherState`、内部`AppId`をそのままAPIへ送らない。[WindowsのAppId](../src/domain/app_id.rs)にはパス由来の識別子が含まれ得るため、「IDだから個人情報を含まない」と扱わない。

[Windowsの`identifier`](../src/workers/app_scan.rs)は製品名であり、[macOSの`publisher`](../src/platform/macos/apps.rs)は著作権等の文字列を含み得る。名前の付いたフィールドを無条件に安全な製品情報と扱わない。

送信用の型を別に定義し、許可した項目だけを構築する。

| 項目 | 方針 |
| --- | --- |
| アプリ参照 | 要求内だけの連番等。ローカルAppIdとの対応表は端末外へ出さない |
| OS | `windows`または`macos`。詳細な端末構成は不要 |
| アプリ名・製品名 | 判定に必要な製品情報だけ。ユーザーが変更したショートカット名や自由記述を無条件に送らない |
| 製品識別子 | 公開製品のBundle ID等として確認できるものだけ。欠落時にパスで代用しない |
| 発行元 | 製品の発行元として正規化できる場合だけ。著作権フィールド全体は送らない |
| 候補 | 必要な製品群の名称と短い説明。候補を作った元のフルパスは送らない |
| バージョン | 初版の送信対象にしない。必要性を検証してから別途判断する |

ユーザー名、メールアドレス、端末ID、会員ID、フルパス、起動引数、検索語、利用履歴、非表示アプリ、画面画像、実行ファイル、文書の内容は送信対象にしない。未対応アプリ以外の全インストール一覧を文脈として添付しない。

明らかな個人名・社内情報・URL・パスを含む項目は除外し、安全な製品情報へ落とせないものは送信しない。文字パターン検査だけで完全な匿名化を保証したとは扱わない。利用前に実際に送る内容を確認・除外できる画面を用意する。

### 5.2 通信経路と記録

初版の構成案は`デスクトップアプリ → 運営ゲートウェイ → AI提供元`とする。ゲートウェイは既存実装として確認されておらず、新規の構築対象である。

- 有料APIの共有秘密鍵をデスクトップバイナリへ埋め込まない。実装時にはゲートウェイ認証、流量制限、予算制限を設ける。
- TLSを利用し、要求・応答の本文、アプリ一覧、キーを通常ログやクラッシュレポートへ出さない。
- 運営者・AI提供元・インフラ事業者が受け取る情報と保存期間を分けて記述する。クライアントのIPをAI提供元へ転送しない。
- ゲートウェイが受け取るIPや認証情報の保存・照合可能性も評価する。プロキシを挟んだだけで「完全匿名」と説明しない。
- 課金や不正利用防止に必要な識別情報がある場合は、判定本文との結合を最小化し、プライバシーポリシーへ反映する。
- 製品情報を学習・広告・利用者プロファイリングへ二次利用しない構成を要求する。提供元契約がこの要求に合うことを確認するまで出荷しない。
- ユーザーによる取り消しや無効化は、送信済み情報を物理的に回収する操作ではない。削除依頼と保存期間の実際の手続きを別に記載する。

初版は判定結果の共有キャッシュや利用者横断の集計を作らない。端末には適用した通常の配置と必要な設定だけを保存する。未適用の生レスポンスはセッション終了時に破棄する。

## 6. 許可の保存と撤回

許可状態は`unasked`、`enabled`、`declined`、`revoked`を区別する。説明バージョン、送信項目バージョン、共有先と目的、許可日時を端末内に記録する。

| 状態・イベント | 挙動 |
| --- | --- |
| 未選択・拒否・撤回済み | 要求も本文付き事前通信も行わない。通常のランチャーは利用可能 |
| 初回の有効化 | 説明後のボタン操作で保存する。保存できなければ通信しない |
| 許可済みで同じ範囲の明示実行 | 同意を再表示せず、処理の開始と中断を示す |
| 起動・スキャン・新規アプリ検出 | 許可済みでも自動実行しない |
| 設定から無効化 | 新規要求と再試行を停止し、可能な範囲で進行中要求を中断する。遅延結果は適用しない |
| 共有先・目的・送信範囲の実質的拡大 | 旧許可をそのまま流用せず、変更点を説明して許可を取り直す |
| モデル版だけの変更 | 共有先や取扱い範囲が同じなら同意を毎回取り直さない。ただし品質評価はやり直す |

設定の無効化は一操作で行えるようにする。一般設定の読み込み失敗や復元不能な許可記録は許可なしとして扱う。既存の別AI機能の許可を流用しない。

## 7. 失敗・競合・不正出力の扱い

| 状況 | 動作 |
| --- | --- |
| オフライン、通信エラー、サービス停止、認証・予算・流量制限 | 端末内の配置を維持し、提案を作れなかった旨だけを表示する |
| 応答待ち | 一回の操作全体の待ち時間上限を初版では5秒とする。これはUX上の設定値であり、サービスの性能保証ではない |
| タイムアウト・キャンセル | 結果を適用しない。自動で無期限に再試行しない。再実行はユーザー操作から行う |
| 未知の候補ID、重複回答、欠損、異常な数値、上限超過 | 応答を不採用とする。例外でグリッドを停止させない |
| `none`、低い採用品質、根拠の矛盾 | 当該アプリを元の位置へ残す |
| プレビューで対象を外した結果、フォルダの対象が1個以下になる | その新規フォルダ案を取り消す |
| 配置改訂・対象変更・許可撤回 | 応答到着時と適用直前に確認し、古い提案を破棄する |
| 保存失敗 | 配置と変更記録を一括でロールバックし、適用成功と表示しない |

サービス応答は信頼しない入力として扱う。テキストをコード・SQL・ファイルパス・起動コマンドとして実行しない。要求サイズ、候補数、アプリ数、並列数には上限を設け、提供元契約と負荷試験に基づく具体値を実装PRで記録する。上限を超えた分を無断で追加送信しない。

## 8. 日本法とMicrosoft Store要件の整理

以下は仕様策定のための確認事項であり、個別サービスの適法性や審査通過の保証ではない。採用するデータフローを前提に出荷時に確認する。

### 8.1 日本の個人情報保護法

個人情報該当性は特定個人の識別可能性と他の情報との容易な照合により判断する。一般的なアプリ名や公開製品IDを識別不能な形で扱う場合と、アプリ一覧が本人情報に結び付く場合は区別する。外部AIを使うこと自体が一律の同意要件になるわけではない。[個人情報保護委員会・通則編（2-1、2-8）](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)

個人関連情報の提供では、提供先が個人データとして取得することが想定される場合の確認義務等を区別する。API本文から氏名を除いただけで、認証・IP・ログとの関係を検討せず「同意不要」と断定しない。同ガイドラインの3-7を参照する。

### 8.2 Microsoft Store

確認日2026-09-25に再取得できた本文は**バージョン7.19（公開2025-09-10、施行2025-10-14）**である。提出時は[公式ポリシー](https://learn.microsoft.com/en-us/windows/apps/publish/store-policies)と[変更履歴](https://learn.microsoft.com/en-us/windows/apps/publish/store-policies-change-history)を確認し、公開日と施行日を区別する。未確認の次期版を施行済みとして扱わない。

| 根拠 | 確認した要求と今回の対応 |
| --- | --- |
| 10.5.1 | Win32製品はプライバシーポリシーが必要。AIの有無にかかわらず用意し、AI追加時は共有先・用途・保存・撤回方法を更新する |
| 10.5.2 | 個人情報の外部共有には説明後の明示的な許可と撤回手段が必要。非個人情報への一律適用と説明しない |
| 10.2.3が参照するMicrosoftの判定基準 | 活動やデータを保存・送信するソフトの通知と同意、利用者の制御を求める。本機能の任意有効化と無効化導線に反映する |
| 10.3、10.4.2 | 審査で外部機能を試せるようにし、通信失敗でもアプリを応答可能に保つ |

参照先: [Storeポリシー](https://learn.microsoft.com/en-us/windows/apps/publish/store-policies)、[MicrosoftのUnwanted software判定基準](https://learn.microsoft.com/en-us/unified-secops/criteria#unwanted-software)。

**本仕様では、アプリ一覧が日本法上必ず個人情報に当たるからではなく、実際の外部送信を知らせ利用者が制御できる製品要件として一度の有効化操作を採用する。** Microsoftが匿名のアプリ一覧について個別に同意不要・必須と回答した事実は確認していない。

自由生成コンテンツを追加する場合はStoreの11.16も別途確認する。本仕様の選択式判定を口実に、将来の生成機能を未申告で追加しない。macOS対応だけを理由にMac App Storeの規約を適用しない。Mac版の配布先が決まった時点で別に確認する。

## 9. 実装の責務

| 層 | 責務 |
| --- | --- |
| 基本機能 | 通信なしで初期配置を完成させる。AIクライアントを依存先にしない |
| 整理補助サービス | 未確定対象、候補、許可、配置世代を扱う。API失敗を通常の結果へ変換する |
| 送信DTO構築器 | 許可項目だけを抽出し、元データとの対応を端末内で管理する |
| AIアダプタ | プロバイダ固有の要求・応答を変換する。配置やSQLiteへ直接書かない |
| 提案検証器 | 候補、個数、重複、改訂、除外条件を検証する。ルール結果を優先する |
| app境界・永続化層 | 説明、有効化、プレビュー、明示適用、取り消し、原子的保存を行う |
| 運営ゲートウェイ | 秘密鍵、流量・予算制限、ログ抑制、提供元との通信を管理する |

## 10. 出荷前に確定する項目

AIの文書化と実装着手は可能だが、以下を未確認のまま外部送信を有効にして出荷しない。基本機能の出荷はこれらに依存しない。

- Jev等の正確なAPI契約、固定するモデル版、商用利用条件、稼働地域、再委託先、学習利用、本文・ログの保存期間、削除手順。
- 日本語・英語、Windows・macOS、既知・未知アプリ、紛らわしい名称、社内アプリに対する精度。採用率と誤収納率を別々に測る。
- 確信度の採用閾値、アプリ・候補の上限、要求サイズ、並列数、API費用の上限。モデル更新時の回帰評価手順。
- 運営ゲートウェイの認証、秘密鍵保管、濫用防止、IP・アクセスログの扱い、障害時の停止手順。
- 実際の共有先と送信項目に一致する説明文、プライバシーポリシー、審査用の動作確認手順。
