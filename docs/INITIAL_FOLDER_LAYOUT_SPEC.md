# 初期フォルダ配置仕様（非AI）

- 作成日: 2026-09-25
- 状態: 初期フォルダ配置と設定リセット時の再適用の実装仕様。
- 対象: Liquid StartのWindows版およびmacOS版。
- 確認したコード: `main` の `d0b4fa7a4214a2f0adb427b3d6ecfb2bf2b50a28`。
- AIによる補完は [AI_FOLDER_ASSIST_SPEC.md](AI_FOLDER_ASSIST_SPEC.md) に分離する。本仕様だけで実装・出荷・利用できる。

## 1. 決定事項

**初回と明示的な設定リセット時に、実在するアプリを分かりやすい製品群・OS標準ツールのフォルダへまとめる。残りは直接表示する。**

| 項目 | 採用する仕様 |
| --- | --- |
| 実行方式 | 同梱プリセットと端末内の情報による決定的な処理。外部通信なし |
| 対応範囲 | 初版の候補は19種類。19個の表示を強制せず、追加可能なカタログとして管理する |
| 作成条件 | 同じグループに異なる起動対象が2個以上ある場合だけ作成する |
| 不明なアプリ | トップレベルに残す。「その他」へ詰め込まない |
| 表示順 | Windowsは日常の入口→作業→一般→管理・補助の優先順。同順位とmacOSは名前順。アプリとフォルダを混在させて保存する |
| 適用機会 | 新しい配置を作る初回、および設定の「設定をリセット」を押したとき。既存ユーザーへの自動適用は行わない |
| その後 | 通常の編集可能なフォルダ。自動で名前・所属・位置を更新しない |
| 追加アプリ | トップレベル末尾に追加する。既存フォルダへ自動投入しない |
| AIとの関係 | AIを有効にしなくても初期配置が完成する。AIの設定・同意・応答を待たない |

「2個以上」とプリセットの初期範囲は今回の製品上の決定であり、実験で最適性を確認済みの数値ではない。

## 2. 目的と対象外

初回から整理作業を要求せず、見覚えのあるアプリを起動できる状態を渡す。フォルダ名と中の小アイコンから内容を予測できることを重視する。フォルダ数や収納率の最大化は目的にしない。

今回のフォルダはアプリの**置き場所**である。[Issue #38](https://github.com/kamakiri1192/windows-launchpad-rust/issues/38) が扱う「同じアプリを複数の用途別カテゴリから探す機能」とは別に実装する。#38を本機能の実装完了として閉じない。

対象外は次のとおり。

- 「仕事」「開発」「クリエイティブ」などによる全アプリの用途別分類、複数カテゴリへの掲載、継続的な自動整理。
- 使用頻度の推定、使用履歴の収集、クラウド同期、プリセットのネットワーク更新。
- スタートメニュー、Dock、Applicationsディレクトリなどの実ファイルやOS設定の変更。
- 未検出アプリのダミータイル作成、プラグインからの起動項目の合成、別製品のインストール。

## 4. 初回の画面と操作

### 4.1 起動から表示まで

1. ウィンドウを先に表示する。スキャンや画像抽出でUIスレッドを停止しない。
2. 保存状態を読み込み、新規配置の対象かを判定する。
3. 初回スナップショットから端末内で配置案を生成する。
4. 配置と初期化記録を保存した上で、アプリを操作できるグリッドを表示する。
5. アイコン画像は既存の非同期経路で順次反映する。画像の到着で所属や並び順を変えない。

「平置きで操作可能にする→処理完了後にアイコンをフォルダへ移動する」という表示は行わない。配置処理を追加するために画像抽出の完了まで待つこともしない。[既存の起動設計](STARTUP_PERFORMANCE.md) を維持する。

### 4.2 グリッドの構成

- Windowsは日常の入口→作業→一般→管理・補助の順に、アプリと作成済みフォルダを混在させる。同順位は表示名の小文字化キーと安定IDによる昇順。macOSは従来の名前順を維持する。詳細は[初期配置の優先順](INITIAL_LAYOUT_ORDER_PROPOSAL.md)を参照する。
- 設定・エクスプローラー・電卓・Store・Chrome・Edge・Discordを直接前方へ置き、Adobe・OBSなどを続ける。存在しないアプリの空き枠は作らない。同じ製品の版違いは代表1件だけを前方へ置く。
- WindowsアクセサリとPC管理の内部は用途順にする。他のフォルダ内は名前順。フォルダが成立しない場合も単体アプリの役割に応じた優先順を使う。
- 名前比較は現行の名前順処理と共通化する。OSの列挙順やハッシュマップの順序を結果へ漏らさない。
- フォルダを先頭や1ページ目の最終行へ固定しない。既存グリッドへ連続配置し、必要なら通常のページングを使う。
- 並び順は初回に確定して保存する。ウィンドウサイズ変更ではセルの再配置だけを行い、保存した論理順序を変更しない。
- 全アプリがフォルダ候補に入る環境でも、見栄えのために一部だけを外へ複製しない。
- 初期フォルダは既存と同じ小アイコンプレビューを持つ。ブランドロゴの追加ダウンロードは行わない。

フォルダの種類が増えても独自の専用画面や固定領域は追加しない。

### 4.3 取り消し

生成済みのフォルダを通常のグリッドとして表示する。

取り消しは設定の「初期整理を取り消す」から行う。分類方針の選択画面やチュートリアルの完了を起動条件にしない。取り消しの有効条件は第8節に定める。

### 5.1 カタログ追加の条件

各エントリは次を持つデータとして管理する。初版はアプリに同梱し、アプリ更新で配布する。

- 安定した`preset_id`、カタログバージョン、対応OS、表示名のローカライズキー。
- 明示した対象製品、完全一致する識別子または複数の根拠を組み合わせた検出条件。
- 除外条件とトップレベル維持条件。
- 根拠資料または確認したインストール結果、正例・誤検出しやすい負例のテストデータ。

追加プリセット（Windowsの実機確認済み）: Git、Unity、Live2D Cubism、Razer、アクセシビリティ。管理・付属ツールも、その製品との関係と起動先を明示して同じフォルダに含める。

候補数に19個の上限は設けない。ただし、メーカーが同じという理由だけの追加は認めない。未確認のエントリは無効のままとし、確認済みの対応範囲を実装PRへ記録する。

表示名はユーザーの言語に合わせる。英語版などでも内部IDは共通にする。保存後は通常のフォルダ名として扱い、言語変更やプリセット改名で既存名を上書きしない。

## 6. 判定とフォルダ生成

### 6.1 使える情報と制約

| 入力元 | 利用する情報 | 注意点 |
| --- | --- | --- |
| [Windowsスキャン](../src/workers/app_scan.rs) | ショートカット名、元の階層、起動先、実行ファイルの製品名・発行元 | `identifier`は製品名であり、普遍的な製品IDではない。発行元文字列だけで決めない |
| [macOSスキャン](../src/platform/macos/apps.rs) | Bundle ID、表示名、アプリの配置場所 | `publisher`は著作権等の文字列由来。署名検証済みの発行元とは扱わない |
| [Steamスキャン](../src/workers/steam_scan.rs) | manifest由来を示す`steam:`のAppId | Steam由来から「ゲーム」という用途は推定しない |

端末内のパスは判定補助に利用できる。外部送信用データとは別物である。

元のフォルダ階層は根拠として利用するが、無条件で複製しない。「Programs」「Applications」やメーカーの共通ディレクトリだけでは所属を決めない。管理者権限の要求や新たな使用履歴収集は不要とする。

### 6.2 優先順位

1. スキャン対象外・非表示・表示設定により除外されるアプリを候補から外す。既存のアンインストーラ等の除外処理を維持する。
2. プリセットの明示的なトップレベル維持条件を適用する。
3. Steam manifest由来の項目は、既知のVR用App IDを`vr-tools`／`vr-games`へ、それ以外を`steam-library`へ分類する。いずれも二重配置しない。
4. 明示した製品識別条件を適用し、次にOS標準ツールの条件を適用する。
5. 同じ優先度の複数グループに矛盾して一致した項目は、いずれにも割り当てずトップレベルへ残す。プリセットの列挙順で解決しない。
6. 不明な項目はトップレベルへ残す。広い部分一致だけで無理に収納しない。

同じ入力・カタログバージョン・表示言語なら、同じ所属と論理順序を生成する。FolderIdは既存の衝突しない生成方法を使い、再起動時は生成し直さず保存したIDを使う。

### 6.3 「2個」の数え方

- 2個以上とは異なる起動対象の数である。同じアプリへの重複ショートカットで閾値を満たさない。
- 同じ実行ファイルでも起動引数が異なる場合は別の機能を起動し得る。実行ファイルのパスだけで重複排除しない。
- 同じ製品のバージョン違いだけでフォルダを増やさない。単一製品の複数版はトップレベルを維持し、製品群として複数の対象製品・付属機能がある場合にまとめる。
- 既存のAppIdや起動処理を変更して重複を解消しない。閾値計算用のローカルな起動同一性を別に求める。
- 起動同一性が不明な重複候補だけでは作成を確定しない。必要な情報の取得は実装上の追加点として扱う。

現行の`SnapshotEntry`には起動引数が含まれていない。必要ならWindowsアダプタからローカル判定用に補助情報を渡す。LibreOfficeやVisual Studioの共有実行ファイルを使う起動項目は専用テストを設ける。

### 6.4 出力の不変条件

フォルダ作成前後で対象アプリの集合を変えない。各表示対象はトップレベルまたは一つのフォルダ内に一度だけ現れる。非表示アプリの再表示、アプリの消失、入れ子フォルダ、空・単一アプリの初期フォルダは禁止する。

内部の判定結果は`Grouped(preset_id)`、`KeepTopLevel`、`Unresolved`を区別する。後二者は同じトップレベル表示になるが、拡張機能が明示的な除外を「判定できなかった」と誤認しないために区別する。

## 7. 初回の判定と保存

### 7.1 適用条件

`customized == false`だけを初回判定に使わない。

| 読み込み状態 | 挙動 |
| --- | --- |
| 新規作成した空のアプリデータ領域で、過去の利用記録がない | 初期配置の対象にする |
| 保存済み配置または旧形式の並び順・非表示設定がある | そのまま復元・移行する。初期配置を適用しない |
| 旧版利用の形跡があるが配置が保存されていない | 既存ユーザーとして平置きを維持する |
| 破損・読み込み失敗・新旧の判定不能 | 初期整理を自動適用しない。元データを上書きしない |
| 初期化済み、取り消し済み、ユーザーによる配置リセット済み | 保存済み配置を復元する |
| 設定の「設定をリセット」を明示的に実行 | 現在検出できているアプリに初期配置を適用し直す |

初回データベース作成の事実と既存キーの有無を読み込み層で取得する。破損を`None`へまとめる既存APIだけでは判定できないため、読み込み状態を区別する拡張が必要である。

### 7.2 追加する保存情報

配置本体は既存の`launcher_state`を正とし、別のフォルダ一覧を正として持たない。補助記録として以下を追加する。

| 情報 | 用途 |
| --- | --- |
| 初期化状態 | `applied`、`completed_flat`、`preserved_existing`、`undone`などの理由を区別する。旧版の`skipped_error`も読み込めるが、不完全スキャンを理由に新しく記録しない |
| 仕様・カタログバージョン | 何を使って初期化したかを記録する。バージョン変更を再整理の条件にしない |
| 初期配置の世代ID | 再実行・遅延処理との混同を防ぐ |
| レイアウト改訂番号 | 配置を変えるユーザー操作、検出差分の統合などで更新する |
| 初期整理の変更記録 | 作成したFolderId、子AppId、整理前後の論理配置、適用後の改訂番号 |

配置と補助記録は同じSQLiteトランザクションで保存する。フォルダ生成または優先順による変更があれば`applied`と取り消し記録を保存する。どちらも変更がない場合は`completed_flat`を記録する。後のインストールやカタログ更新で初期化をやり直さない。

初期配置を保存できなければ、整理済みと偽って確定せず平置きで利用可能にする。同じ起動中に再試行結果で勝手に配置を変えない。既存データの修復や全消去を本処理の副作用にしない。

### 7.3 不完全な検出

現行スキャナの返すmapだけでは、空の正常結果と検出失敗を十分に区別できない。初期配置に必要なソースごとの完了・失敗情報を追加する。

最初のスキャンが返した取得済みアプリを対象に、一度だけ初期配置を確定する。一部のショートカットやソースを読み取れなくても、取得できたアプリのフォルダ化と優先順を適用する。利用していないSteamや存在しない任意ディレクトリは失敗と扱わない。失敗情報は診断と既知アプリの削除判定に使い、初期整理を止める条件にはしない。

後から検出できた項目はトップレベル末尾へ追加する。既存フォルダへの自動投入や配置の再生成は行わない。取得結果が0件の場合も空の初期配置として保存し、後から見つかったアプリは同じ規則で追加する。既存配置・旧形式・破損データの保護は7.1の判定を維持する。

スキャン自体が終わらない場合もウィンドウは操作可能に保つ。初期配置機能のために無限待機や追加の通信待ちを設けない。

## 8. 取り消しと、その後の運用

### 8.1 初期整理の取り消し

設定の「初期整理を取り消す」は初期整理だけを戻す操作であり、設定全体のリセットではない。

- 初期整理適用後の改訂番号と現在値が一致し、配置が変更されていない間だけ実行できる。
- 設定の「初期整理を取り消す」は、有効な間は再起動後も利用できる。
- 初期整理で作ったフォルダだけを解体し、保存した整理前の名前順へ戻す。設定・アイコンキャッシュ・非表示状態は変更しない。
- フォルダを作らず並び順だけ変わった場合も取り消せる。
- 配置を変更する操作や検出差分の統合が発生したら取り消しを無効にする。古いスナップショットで後の変更を上書きしない。アイコン画像の更新だけでは無効にしない。
- 取り消し後は`undone`を保存する。次回起動時に再作成しない。無効になった後は通常のフォルダ編集で変更する。

### 8.2 通常利用

初期化の終わった配置は、フォルダ数が0でも保存済みの明示的配置として扱う。現行の`customized`による名前順再統合で順序が書き換わらないようにする。

新規アプリは同じスキャンで追加された項目同士を名前順にして末尾へ追加する。取り出したアプリを自動でフォルダへ戻さない。削除・再発見時の参照保持と復帰位置は既存設計を維持する。

Steam表示の切り替え、カタログ更新、OS更新、言語変更、モデル追加、キャッシュ再構築で自動整理を再実行しない。ユーザーが明示的に選ぶ「名前順」などの通常機能は利用できるが、フォルダの所属まで再計算しない。

「設定をリセット」は、設定値と非表示状態を初期化し、現在検出できているアプリに初回と同じ生成処理を適用する。スキャンの一部が不完全でも、明示操作では取得済みのアプリを対象にする。新しい改訂番号と取り消し記録を保存し、次回起動ではその配置を復元する。設定と配置の保存に失敗した場合は、操作前の状態を維持する。

アイコンキャッシュ削除は初期化記録を消さない。アプリデータの完全削除後の再インストールは新規領域として扱う。

## 9. 実装の責務

| 層 | 責務 |
| --- | --- |
| OSアダプタ・スキャナ | 既存の検出範囲内で判定材料とスキャン成否を返す。UI・外部APIを呼ばない |
| プリセットカタログ | OS別の明示ルール、除外、名称、根拠、テストケースを管理する |
| domainの初期配置生成器 | スナップショットから検証可能な配置案と変更記録を返す。純粋な処理にする |
| app境界 | 初回判定、現在の改訂番号の確認、初期配置の適用、設定からの取り消しを調停する |
| 永続化層 | 配置と記録を原子的に保存する。未保存と破損を区別する |
| 既存renderer・folder機能 | 通常のアプリ・フォルダとして描画・編集する。プリセットやAI固有の判定を持たない |
