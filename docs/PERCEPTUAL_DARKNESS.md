# Dynamic Darkness: 同一フレームの局所トーン補正

2026-09-28 / 基準 main: `a8ecf7f27c979982fe9335f0a639bfd453dfacda`

## 採用判断と検証状態

**採用案は、線形RGBの色度を保存する、局所・連続・履歴なしの有理トーンカーブ。**
画面全体の「白の面積」から一つの暗化率を決める方式を、通常のガラスの最終フラグメント内で
各位置の明るさを補正する方式へ変更する。AI推論・ヒストグラム・追加画像サンプル・追加描画パスは不要。
既存の背景取得、ぼかし、屈折、色付け、彩度、縁の照明、アルファ合成は維持する。

これは Apple の非公開実装の再現ではない。また、主観的な「自然さ」の普遍的最適解を証明したものではない。
ここでの選択基準は、明るい有彩色にも反応すること、暗部を大きく潰さないこと、
離れた場所の明暗に連動しないこと、階調を逆転させないこと、補正にフレーム履歴を持たないこと。

| 検証 | 状態 |

## Apple の公開資料から採った原則

調査時の公式製品ページは iOS 27 / macOS 27 Golden Gate。
最新ページでは Liquid Glass の屈折・コントラストの改善と、不透明度・色合いの調整が案内されている。

WWDC25 の技術説明では、背後の内容に応じた色調・影・明暗レンジの調整、
Regular と Clear の違い、大きいメニューやサイドバーで気を散らす明暗反転を避けること、
ガラスをむやみに重ねないことが説明されている。
公開資料は正確なトーンカーブ、係数、サンプリング密度、時間フィルターの実装までは規定していない。
したがって以下の式は、このアプリ向けの独立した設計である。

## 比較した5方式

| 方式 | 長所 | 今回の要件に対する問題 |
|---|---|---|
| 現行 white coverage | 白い画面への限定的な補正。従来互換 | 彩度による除外、狭い白領域の見落とし、時間遅延 |
| Coverage tuned（#198の係数） | 白面積への感度を改善 | 有彩色を除外する構造と、全体連動は残る |
| 平均相対輝度による上限制御 | 有彩色を正しい輝度で評価 | 暗い領域で希釈され、離れた場所の影響を受ける |
| 75%分位相対輝度による上限制御 | 半々の明暗背景を拾いやすい | 25%前後の明部面積で統計が急変し、局所的な白領域を見落とす |
| **局所有理カーブ** | 有彩色・局所明部・連続階調・履歴なし | フラグメントの演算量が増える。GPU時間の実測が必要 |

公平のため、CPU比較のcoverageは全コーパス画素を利用し、256点の疎なサンプリングによる
不利を与えていない。平均・分位方式は線形RGBで `Y_target=0.20` を評価し、
白の暗化量が同じになる下限ゲインで制限する。これは色空間を正しく扱う比較実装であり、
PR #198 の実行ファイルを動かしたという意味ではない。

白色の減衰量を共通にした比較であり、好みのラベルを正解として最適化したスコアではない。
局所方式は、暗い部分に囲まれた15%の白領域にも反応し、
その白領域の面積に応じて残りの暗部まで一斉に暗くすることがない。

## 数式

入力 `C` は、このレンダラーのUnorm経路で扱う、表示参照のsRGB相当RGB。
現在のTint/Saturation処理を終えた値を使う。これはレンダラー全体を線形合成へ変更するPRではない。
sRGBテクスチャによる自動デコードを将来導入する場合は、この契約も変更し、二重デコードを避けること。
HDR/PQ/HLG/広色域の正しい色管理を、この変更だけで保証してはいけない。

```text
c = sRGB_decode(C)
Y = dot(c, (0.2126, 0.7152, 0.0722))
a = sRGB_decode(1 - clamp(auto_max, 0, 1))
g(Y) = a / (a + (1 - a) * clamp(Y, 0, 1))
C_auto = sRGB_encode(c * g(Y))
```

上限0は恒等変換、上限1は黒への変換として個別処理する。
黒の除算を避け、手動・自動とも0の経路では従来値をそのまま返す。

SDRの `0 <= Y <= 1` では:

- `Y_out = aY / (a + (1-a)Y)` は単調増加。導関数は `a² / (a+(1-a)Y)²`。
- `Y→0` でゲインは1。暗部の傾きも1へ近づき、シャドウを強く潰さない。
- 白 `C=(1,1,1)` は厳密な式では `C_out=(1-auto_max)` となる。
- 線形RGBの3成分に同じ正の係数を掛けるため、自動補正は色度を保存する。
  知覚的な彩度や「自然さ」が全観察条件で不変だと主張するものではない。

`auto_max=0.16, manual=0` のCPU結果（他のガラス効果を含まない）:

| 入力sRGB | 出力sRGB |
|---|---|
| 白 `(1,1,1)` | `(0.8400,0.8400,0.8400)` |
| 黄 `(1,1,0)` | `(0.8489,0.8489,0)` |
| 緑 `(0,1,0)` | `(0,0.8771,0)` |
| 青 `(0,0,1)` | `(0,0,0.9850)` |
| 灰 `(0.5,0.5,0.5)` | `(0.4777,0.4777,0.4777)` |
| 暗灰 `(0.1,0.1,0.1)` | `(0.09969,0.09969,0.09969)` |

上限の意味は**白の端点におけるsRGB減衰量**。有彩色の各チャンネルを必ず16%以内で減衰させる
という意味ではない。色度保存の線形減衰と、従来の符号化RGBの黒オーバーレイは異なる。

### 手動値との関係

手動値の従来動作 `C_manual = C*(1-manual)` は維持する。
自動側の目標輝度を `Y_auto`、手動後の輝度を `Y_manual` とし、
`Y_manual <= Y_auto` なら手動結果をそのまま返す。
そうでない場合だけ、手動結果の線形RGBを `Y_auto/Y_manual` 倍する。

したがって手動値より明るく戻さず、自動値と手動値を黒オーバーレイとして加算しない。
有彩色でも切り替えが連続する。手動の符号化RGB処理がもともと持つ色変化は互換性のため残る。

### 演算量

再エンコードの非線形部分は、減衰ゲインが1以下であることを利用して
`(C_manual + 0.055)*pow(gain,1/2.4)-0.055` と変形し、通常経路では
3成分別のencode powerを1個のスカラーpowerへ減らす。
sRGBの丸められた境界値にある微小な重なりは、通常の成分別変換へ戻して扱う。
追加テクスチャ参照・別フレームの履歴・GPUからCPUへの同期読み戻しはない。
旧方式も描画のためのCPU読み戻しは行っておらず、主要な応答遅延は時間フィルター由来だった。

## 描画とHUDを分離する

```text
最新の取得済み背景 → 既存blur/屈折/Tint/Saturation
                   → 局所色補正 → 既存rim照明 → 既存alpha合成

背景の16×16サンプル → 診断用の平均 → 非同期readback → HUDのみ
```

最終シェーダーの通常面と縁の両経路で同じ関数を呼ぶ。
トグルの透明レンズ `fs_toggle` には追加しない。
既存のバッファサイズ・バインディングは変えない。

HUDは `Dynamic Darkness (capture mean)` と表示し、各サンプルの輝度を同じカーブで補正したときの
「等価な無彩色sRGB暗化率」の平均を示す。生のキャプチャの疎なサンプルであり、
面別・画素別の実際の適用値、手動値との合成後、アルファ合成後、文字コントラストを示すものではない。
Full rate / Adaptive / 固定8Hz は**この診断統計の更新頻度**にのみ関係し、描画の追従を制限しない。

### 面ごとの適用範囲（2026-09-29更新）

設定パネルとコンテキストメニューパネルは`auto_darkness_enabled = 0`を面別uniformへ設定し、
Dynamic Darknessの局所補正を直接適用しない。それぞれの専用手動Darknessは引き続き適用する。
設定パネルと描画経路を共用するフォルダパネルは、この無効化の対象に含めない。
ページ・フォルダ・下部コントロール等は共通の自動ON/OFF設定に従う。
設定つまみの透明レンズは従来どおり直接適用しない。

設定パネル・コンテキストメニューのcompleted-scene入力は変更しない。
下層で適用済みの暗さは背景画像として引き継ぎ、逆算して除去しない。
その上にパネル専用の手動Darknessを適用した場合は、暗さがさらに重なる。
ガラスの重なり設計を変える場合は、元のscene入力を分離する別の検証が必要。
面別の無効化は新しい保存設定を追加しない。共通の自動Darknessの初期値はONで、保存済みのOFFは維持する。

## 1フレーム要件の判定

**実装上の性質**: 取得済みの背景を描く同じ最終パスで色を決定する。
旧値の収束待ちや次フレームへの受け渡しを追加しない。
`src/app/frame.rs` のドラッグ中の背景取得停止も外し、決定論的QAの停止指定だけを残す。

**まだ実証していない事項**: GPU処理時間が全対象機でフレーム予算内に収まること、
OSが背景を更新してから画面に表示されるまでのend-to-end遅延。
取得・コピー・blur・全レイヤー合成・present・OSコンポジターを含めて測定する必要がある。
「履歴0フレーム」は「処理時間0ms」でも「取得から表示までの遅延0」でもない。

リリース前の受け入れ条件:

1. `cargo fmt --all -- --check`、`cargo test --test perceptual_darkness`、
   `cargo test --test wgsl_validation`、全テスト・Clippy・release buildを通す。
2. Windows/D3D12の実機で1080p/4K、60/120Hz、通常面・設定・メニュー・ドラッグを測定する。
   白黒切替、移動する白窓、飽和色、ノイズを含む動画を使い、GPU区間とフレームIDを記録する。
3. p50/p95/p99・最悪値・欠落フレームを、変更前後の同じ機器/設定で比較する。
   全フレーム予算は60Hzで16.67ms、120Hzで8.33ms。CPU参照計算の時間をGPU時間として代用しない。
4. 色調の好みと読字を実機で確認する。上限0.16・透過合成・白文字の組み合わせについて、
   この変更だけでアクセシビリティのコントラスト基準を保証しない。

## 再現

```sh
python -m pip install numpy pillow
python qa/perceptual_darkness.py --out target/perceptual-darkness
cargo test --test perceptual_darkness
cargo test --test wgsl_validation
```

Python検証はローカルの合成データだけを使い、外部通信やデスクトップ画像の送信を行わない。
Pillowがなければ画像生成だけを省略し、数値検証は実行する。
GPU一致テストは実際の生産用WGSL関数を実行する。GPUが取得できなければ失敗とし、
CPUだけで成功したように扱わない。
